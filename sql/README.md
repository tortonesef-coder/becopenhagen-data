# What is in here

Two kinds of file, and mixing them up is how a build breaks.

## Runs every time

Executed by `scripts/build-warehouse.sh` on the hourly refresh. Editing one of
these changes the warehouse within the hour.

    build-warehouse.sql        the bc.* layer, from the fleet snapshot + archive
    build-catalog-views.sql    copies the hand-curated catalog tables into bc.*
    build-uploads.sql          GENERATED by src/ingest.js. Do not edit by hand.
    resolve-guides-post.sql    attaches guide identity after resolve-guides.js

## Defines the catalog

Applied when the catalog is built or extended. Re-runnable: each is written to
be idempotent, because a seed that is not idempotent gets run twice eventually
and quietly reverts a decision somebody made by hand.

    catalog-schema.sql         the section 3 tables
    catalog-doubts.sql         the doubts queue
    catalog-usage.sql          source usage and curator proposals
    catalog-definitions.sql    the agreed meaning of each word
    catalog-assertions.sql     the checks that catch a wrong number
    catalog-canonical.sql      the standard answer to a common question
    catalog-corrections.sql    corrections captured from people
    catalog-gaps-v2.sql        the amendment's gap schema
    catalog-gaps-seed.sql      the gap catalogue
    catalog-seed.sql           sources and their gotchas

## applied/

One-off migrations that have already been run. They are kept, not deleted,
because each one carries WHY it was needed, and that reasoning exists nowhere
else. They are not re-run and nothing references them.

Kept separate so that "which files actually run?" has an obvious answer. A
directory where the live build files sit next to four spent migrations is a
directory nobody trusts.
